# مَدَار | ERP للصيانة والتشغيل

نظام ويب محلي لإدارة العملاء وأوامر التشغيل والصيانة والماكينات والصور والمخزون. التطبيق وقاعدة البيانات داخل `system/`، بينما تبقى ملفات العملاء والصور في `storage/` منفصلة عن تحديثات الكود.

## التطوير المحلي على Windows

1. ثبّت Node.js 22 أو أحدث؛ الحد الأدنى معلن في `package.json` ومتوافق مع `better-sqlite3` المثبت.
2. انسخ `.env.example` إلى `.env` في مجلد المشروع، واضبط `JWT_SECRET` إلى قيمة عشوائية خاصة (باستخدام الأمر المرفق في المثال) مرة واحدة. عدّل `STORAGE_ROOT_PATH` و`DATABASE_URL` إذا رغبت.
3. نفّذ `cd system` ثم `npm install`.
4. نفّذ `npm run dev` وافتح `http://localhost:5173` للواجهة الساخنة أثناء التطوير. في أول دخول، أنشئ حساب المدير العام من شاشة الإعداد الأولي. خادم API يعمل على `PORT` (3100 افتراضيًا).

في التطوير، `npm run dev` يشغّل Vite وواجهة API. للتشغيل المباشر/PM2، نفّذ خطوات التجهيز صراحةً من `system/` قبل بدء الخدمة: `npm install` ثم `npm run build`. `npm start` يفشل برسالة واضحة إن كانت التبعيات أو الواجهة المبنية مفقودة؛ لا يثبت أو يبني أثناء بدء الخدمة. افتح `http://localhost:<PORT>`؛ مجلدات `storage/Areas` الجديدة تصدر حدث Socket.IO باسم `areas:folder-added`.

يدعم النظام SQLite محليًا (`DATABASE_URL=file:...`)؛ المسارات النسبية تُحل من جذر المشروع. يستخدم SQL المباشر `better-sqlite3` وتستخدم معاملات/نماذج Sequelize محرك SQLite عبر `sqlite3` على **ملف قاعدة البيانات نفسه**. لا تضع مجلد `storage/` داخل `system/` عند نقله أو نسخه احتياطيًا.

## النشر المخطط على Ubuntu

Ubuntu بيئة مستهدفة لاحقًا وليست بيئة التطوير الحالية. لم يُتحقق هنا من توافق Ubuntu أو من استعادة فعلية عليه. لا تنسخ بيانات الإنتاج إلى بيئة الاختبار؛ استخدم قاعدة وتخزينًا ونسخًا احتياطية اصطناعية منفصلة.

على Ubuntu، ثبّت Node.js 22+ وPM2، ثم نفّذ من `system/` `npm ci` و`npm run build` قبل تشغيل `npx pm2 start ecosystem.config.js` من جذر المشروع، ثم `npx pm2 save`. لإعادة التشغيل بعد إقلاع النظام، نفّذ `npx pm2 startup` واتبع الأمر الذي يطبعه PM2. إعداد PM2 الحالي عملية واحدة بنمط fork؛ لا تضاعف النسخ مع SQLite المحلي. `system/index.js` يفحص المتطلبات ولا يثبت الحزم أو يبني الواجهة أثناء بدء الخدمة.

أنشئ مستخدم خدمة مخصصًا بأقل صلاحيات لازمة: قراءة ملفات البرنامج والواجهة المبنية وملف إعداد الخدمة، وكتابة قاعدة SQLite ومجلدات `storage/` و`Backups/` وذاكرة الصور والسجلات المرحلية. قيّد قراءة `.env` على مستخدم الخدمة والمسؤولين فقط. يبقى `HOST` على loopback افتراضيًا. لا تضبط `HOST=0.0.0.0` إلا عند الحاجة إلى الوصول الشبكي، واقصر الوصول بجدار ناري/شبكة موثوقة واستخدم HTTPS عبر reverse proxy واضبط `COOKIE_SECURE=true`. `TRUST_PROXY_HOPS` افتراضيًا `0`؛ اضبطه فقط على عدد الوكلاء الموثوقين الفعلي (من 0 إلى 5). الحساب الأول يُنشأ من شاشة الإعداد الأولي؛ لا تعرض الخدمة للشبكة قبل إتمام الإعداد. استخدم إيقافًا منظمًا عبر PM2/SIGTERM ودع التطبيق يغلق المجدول ومراقب الملفات واتصالات SQLite.

### قائمة تحقق لبيئة Ubuntu المعزولة

1. استخدم VM/مضيف اختبار معزولًا ونسخة كود نظيفة، دون نسخ `.env` أو `storage/` أو `Backups/` أو قاعدة البيانات أو ملفات الاستيراد القديمة من الإنتاج.
2. أنشئ إعدادًا خاصًا بالاختبار مع `JWT_SECRET` مؤقت، ومسارات قاعدة/تخزين/نسخ وسجلات منفصلة، وبيانات اصطناعية فقط.
3. ثبّت Node 22+، ثم نفّذ `npm ci` و`npm test` و`npm run check` و`npm run build` من `system/`. تحقق من صلاحيات مستخدم الخدمة ومساراته.
4. شغّل نسخة PM2 واحدة، وأكمل الإعداد الأولي قبل فتح أي منفذ. اختبر الجدار الناري والـ reverse proxy وTLS و`TRUST_PROXY_HOPS` وتسجيل الدخول/الخروج وإبطال الجلسة.
5. أنشئ نسخة احتياطية تجريبية، وتحقق من شاشة حالة النسخ والمساحة، ثم استعد النسخة الاصطناعية فقط. افحص السجلات والملفات المستعادة، ثم اختبر إعادة تشغيل PM2 والإيقاف المنظم.
6. اختبر استرداد عمليات الملفات المتقطعة على بيانات الاختبار، وسجّل نتائجها وملاحظات الصلاحيات/الأقفال. قِس زمن الاستعادة قبل اقتراح RPO/RTO. لا تعتبر Ubuntu جاهزًا قبل اجتياز هذا الاختبار ومراجعته.

## الوحدات المتاحة

- دخول وصلاحيات: مدير، مبيعات، تشغيل وصيانة، مشتريات ومخازن.
- العملاء وأكوادهم ومجلداتهم، وأوامر التشغيل والصيانة مع فصل تكلفة الخامات والتشغيل عن قيمة البيع وهامش الربح.
- استيراد الماكينات من CSV/XLSX، ورفع مجلد صور المنطقة، ومطابقة المجلدات غير المعروفة.
- توزيع الصور زمنيًا بين قبل/بعد مع تعديل يدوي، أسباب صيانة، واعتماد ونقل الصور للأرشيف.
- مخزن أساسي للوحدات الكاملة ومخزن للبواقي، وتسوية تلقائية للاستهلاك الكسري مع سجل حركة لكل مخزن.
- استيراد جرد CSV/XLSX وتصديره إلى Excel، وفواتير شراء/مبيعات منفصلة عن حركة النقد؛ تُسجل المقبوضات والمدفوعات بسندات مستقلة.
- لوحة مالية تعرض الوارد والمنصرف وصافي السيولة والتدفق الشهري والأرباح المتوقعة وقيمة أصول المخزون.
- مراقبة مجلد `storage/Areas` لحظيًا، مع قائمة REST للمجلدات الحالية وإشعار Socket.IO عند إضافة مجلد جديد.
- مراجعة صور الماكينات بصور WebP مصغرة افتراضية، تحديد جماعي عبر Shift، سحب وإفلات، معاينة مكبرة، وبحث سريع بـ Ctrl+K ووضع ليلي.
- إدارة أسباب الصيانة والمستخدمين.
- تصدير التقارير إلى PowerPoint وWord، والطباعة أو الحفظ كـ PDF من المتصفح.

تُحفظ كلمات المرور مجزأة. جلسة JWT مدتها سبعة أيام وتُسجل بصمة توكنها لإبطالها عند تسجيل الخروج؛ تستخدم محاولات الدخول تأخيرًا تدريجيًا محدودًا داخل العملية الواحدة. يحتفظ التطبيق بنموذج الأدوار الحالي؛ الاستخدام المقصود حاليًا للمستخدمين الإداريين. قراءات الملفات تتطلب تسجيل الدخول وتتحقق من جذر التخزين والروابط الرمزية، لكنها لا تطبق نطاقًا حسب العميل. استيراد المستخدمين يتم في الذاكرة ولا يحفظ الملف في التخزين؛ ملفات الاستيراد القديمة المطابقة تُخفى من التصفح وتُستثنى من النسخ المستقبلية دون حذفها. لوحة الإعدادات تعرض حالة آخر نسخة ومساحة القرص وعمليات الاسترداد المعلقة. النسخ لا تزال محلية على وسيط التشغيل ولا توجد سياسة احتفاظ أو وجهة مستقلة معتمدة.

### إعدادات رفع الصور

- `PHOTO_UPLOAD_MAX_REQUEST_BYTES`: الحد الأقصى لحجم طلب رفع الصور متعدد الملفات كاملًا (الافتراضي 1 GiB).
- `PHOTO_UPLOAD_MAX_CONCURRENT`: أقصى عدد طلبات رفع صور متزامنة للعملية الواحدة (الافتراضي 2، مع منع عمليتي رفع متزامنتين للأمر نفسه).
- `PHOTO_UPLOAD_STALE_TEMP_MS`: عمر ملفات الرفع المرحلية المعزولة قبل تنظيفها عند بدء التشغيل (الافتراضي 24 ساعة). لا يُنظّف إلا مجلد مرحلي يحمل علامة Madar ويحتوي ملفات بأسماء الرفع المتوقعة.

### قرارات سياسة النسخ — تنتظر موافقة المالك

لم تُعتمد وجهة أو مدة احتفاظ أو RPO/RTO، ولا يحذف النظام نسخًا تلقائيًا. على المالك الاختيار بين نسخ على القرص نفسه (الخيار الحالي والأضعف عند تعطل المضيف)، وسيط محلي منفصل/قابل للإزالة، وجهة داخلية موثوقة على الشبكة، أو وسيط غير متصل مع تشفير وإدارة منفصلة للمفتاح. كما يلزم تحديد عدم الحذف التلقائي أو حد/مدة احتفاظ بعد تقدير السعة، وتحديد جدول النسخ وRPO الذي يحققه فعليًا، ثم تحديد RTO بناءً على تمرين استعادة مقاس. لا تحذف نسخًا قديمة قبل اعتماد القرار.

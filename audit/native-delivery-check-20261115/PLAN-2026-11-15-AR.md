## 1) القرارات المثبتة

1. **اعتماد المندوب = تسليم + اعتماد تلقائي بشروط.**
   - المندوب يضغط زرًا واحدًا: «اعتماد وإرسال».
   - السيرفر يعتمد فورًا فقط لو كل شروط السلامة مستوفاة.
   - لو شرط فشل: الزيارة تفضل `pending` وتظهر للمشرف مع سبب واضح.
   - الصلاحية `can_self_approve_visits` مقفولة افتراضيًا وتُفعّل لكل مندوب من لوحة الإدارة.

2. **تعديل موقع الماكينة = طلب من المندوب + موافقة الأدمن.**
   - المندوب يرسل الطلب مباشرة من التطبيق (بدون وسيط مشرف).
   - الطلب لا يغيّر `machines.latitude/longitude` فورًا.
   - الأدمن يوافق أو يرفض، وبعد الموافقة فقط يتطبق الموقع الجديد.
   - هذا هو تفسيري لعبارة «مباشر من المندوب + موافقة الأدمن»؛ لو المقصود أن يتطبق فورًا ثم يراجعه الأدمن، فهذا تغيير في قواعد العمل ويحتاج تأكيدًا صريحًا.

3. **البلاغات = لوحة إدارة + ملف ZIP/Excel + GitHub Issue.**
   - التطبيق يرسل البلاغ للسيرفر فقط، ولا يتصل بـGitHub مباشرة.
   - السيرفر يخزن البلاغ والمرفقات، ويُنشئ Issue اختياريًا.
   - لو GitHub فشل، البلاغ يظل محفوظًا ويظهر خطأ المزامنة في لوحة الإدارة مع زر إعادة محاولة.

## 2) نقاط يجب تثبيتها قبل التنفيذ

### 2.1 مفتاح التوقيع (العائق الأكبر)

المطلوب واحد من الآتي:

- **الأفضل:** keystore الـRelease الأصلي الذي شهادته `f4c8bffc9f852ea6056e350b65156eb880d05629991682492159b9e3937c02a1`، مع `storePassword` و`keyAlias` و`keyPassword`.
- أو keystore الـDebug القديم بشهادة `6b7662b9baf48dc6a00c44911b5bc4e0d2eb7693083b71458c5cf9bd8e5d87d1` لو الأجهزة الحالية مثبتة بنسخة debug قديمة ونريد تحديثًا في المكان.
- لو لا يوجد أي منهما: لا يمكن عمل تحديث in-place للتطبيقات المثبتة. الحل يكون تصدير بيانات الجهاز ثم إلغاء تثبيت وإعادة تثبيت النسخة الجديدة، أو تغيير اسم الحزمة (غير مُفضّل).

> مهم: البحث المحلي لم يجد إلا `debug.keystore` الخاص بهذا الجهاز. لازم البحث في السيرفر القديم، أرشيف البناء، أو أي جهاز تم عليه بناء إصدار 2.0.1/2.2.0.

### 2.2 معنى تعديل الموقع

مطلوب تأكيد: هل الطلب يظل `pending` ولا يتغير الموقع إلا بعد موافقة الأدمن؟ (هذا هو المقترح والافتراضي في الخطة). أم يتطبق فورًا ويراجعه الأدمن بعد ذلك؟

### 2.3 الوصول للسيرفر

مطلوب SSH key أو كلمة مرور لحساب `madar`، أو موافقة على أنك تنفّذ أوامر النشر بنفسك. بدون ذلك يمكن تجهيز الكود محليًا فقط، ولا يمكن النشر أو اختبار التحديث الحقيقي.

### 2.4 GitHub

- المستودع الحالي: `carloshanywork-stack/carlos-madar`.
- مطلوب Fine-grained PAT على هذا المستودع فقط بصلاحية **Issues: Read and write** و**Metadata: Read**.
- هل المستودع Private؟ لو نعم، الـToken لازم يكون عنده وصول له.
- هل تريد إنشاء Issue لكل بلاغ جديد تلقائيًا، أم فقط للبلاغات ذات الخطورة العالية؟

### 2.5 شروط الاعتماد التلقائي (مقترح)

- عدد الصور: الحد الأدنى الحالي للسياسة (صورة قبل + صورة بعد)، وبحد أقصى 20 لكل مرحلة.
- دقة GPS: 30 مترًا أو أفضل.
- داخل نطاق الماكينة مع احتساب هامش الدقة.
- الموقع غير مزيف (Mock) وحديث (أقل من 5 دقائق).
- الماكينة نشطة، والبطاقة/الأمر غير مؤرشفين، ولا يوجد طلب تصحيح معلّق.
- المندوب نشط، والصلاحية مفعّلة، والحد اليومي لم يُتجاوز.
- لو أي شرط فشل: تروح للمشرف مع سبب مثل `GPS_INACCURATE` أو `OUTSIDE_GEOFENCE`.

هذه القيم قابلة للتعديل من إعدادات السيرفر، والمقترح هو الافتراضي.

## 3) المفاتيح والصلاحيات المطلوبة

| المفتاح/الصلاحية | الحالة | مكانه/طريقة التحقق |
|---|---|---|
| Release keystore `f4c8...` | **غير موجود محليًا** | `keytool -list -v -keystore <file> -alias <alias>` ثم طابق SHA-256 |
| Debug keystore `6b7662...` | غير موجود | مطلوب فقط لو تحديث تطبيقات debug قديمة في المكان |
| Debug keystore الحالي `4819...` | موجود | `C:\Users\Carlos.wok\.android\debug.keystore` — للاختبار المحلي فقط |
| `android/key.properties` | غير موجود | يُنشأ من `key.properties.example`، لا يُرفع على Git |
| SSH `madar@100.115.125.88` | مرفوض حاليًا | مطلوب key/password أو تنفيذ يدوي |
| `MADAR_V2_JWT_SECRET` | موجود على السيرفر | 64 حرفًا hex؛ لا يُغيَّر عشوائيًا لأنه يبطل الجلسات |
| GitHub PAT | مطلوب | Fine-grained، Issues RW، يُحفظ في `.env` السيرفر فقط |
| `MADAR_REP_SIGNER_SHA256` | جديد (غير سري) | يُضبط على شهادة التوقيع المعتمدة لمنع نشر APK بشهادة أخرى |
| JDK 21 + Android SDK 36 | موجودة مؤقتًا | الأفضل تثبيت دائم خارج مجلد temp |

**قاعدة أمان:** لا تُرسل كلمات مرور أو keystore في الشات. ضع الملف خارج المستودع، وأنشئ `android/key.properties` بنفسك، أو استخدم طلب سرّي في البيئة.

## 4) المراحل

### المرحلة 0 — تثبيت الأساس (1–3 أيام، تعتمد على الوصول)

**الهدف:** إزالة الغموض قبل كتابة كود جديد.

- سحب `origin/main` والوصول إلى `6f4cd21` أو أحدث.
- فحص شهادة التطبيق المثبت على كل هاتف مستهدف:
  - `adb shell pm path com.madar.rep.app`
  - سحب الـAPK وتشغيل `apksigner verify --print-certs`.
- البحث عن keystore المطابق في السيرفر/الأرشيف. لو غير موجود: اختيار مسار إعادة التثبيت وتوثيقه.
- الحصول على وصول السيرفر، أخذ Backup للداتابيز والتخزين، وفحص `git status` على السيرفر لأن `sourceDirty=true`.
- إنشاء GitHub PAT واختباره بإنشاء Issue تجريبي ثم حذفه.
- تثبيت قرارات الاعتماد والموقع في ملف قرارات.

**مخرج المرحلة:** مسار تحديث موقّع مثبت، أو قرار موثق بإعادة التثبيت؛ وصول سيرفر؛ Token يعمل؛ قرارات مكتوبة.

### المرحلة 1 — السيرفر + لوحة الإدارة + البلاغات + نشر APK

**الهدف:** تجهيز كل ما يحتاجه التطبيق قبل تعديله.

- Migrations جديدة: بلاغات، مرفقات، أحداث، صلاحيات اعتماد، `review_source`، طلبات تغيير الموقع، إصدارات APK، إعدادات.
- API للبلاغات: إنشاء/عرض/تحديث/تصدير Excel/تحميل ZIP + GitHub Issue + إعادة محاولة.
- محرك الاعتماد التلقائي على السيرفر + سبب الفشل + Audit.
- API لطلبات تغيير الموقع + موافقة/رفض الأدمن + إشعار المندوب.
- نشر APK موثّق: allowlist لشهادة التوقيع، سكربت نشر، تاريخ إصدارات، لوحة إصدارات، rollback.
- لوحة إدارة: صفحة «الدعم والبلاغات»، إعدادات الإصدار، مفاتيح صلاحيات المندوب، طابور طلبات الموقع.
- اختبارات كاملة + بناء العميل + عدم لمس الإنتاج.

**مخرج المرحلة:** `npm test` ينجح، العميل يبني، سيناريوهات curl تعمل، لوحة الإدارة تعمل محليًا، ولا نشر إنتاج.

### المرحلة 2 — التطبيق: واجهة أبسط + إعدادات + صلاحيات + بلاغات + تحديث

**الهدف:** تحويل التطبيق إلى واجهة واضحة وربطه بالـAPI الجديد.

- تبويبان فقط: «شغلي» و«الخريطة»، وزر «حسابي» أعلى الشاشة.
- نقل الحضور/الإشعارات/المزامنة/الصحة إلى «حسابي».
- شاشة إعدادات: الإصدار، حالة المزامنة، الصلاحيات، البلاغات، التحديث، تسجيل الخروج.
- طلب الصلاحيات في سياقها: كاميرا عند أول زيارة، موقع عند أول اعتماد، إشعارات بعد أول تسليم، تثبيت التطبيقات عند أول تحديث فقط.
- نموذج بلاغ: وصف + نوع + خطورة + سكرين شوت اختياري + معلومات الجهاز واللوج، مع طابور Offline.
- كارت التحديث: فحص، تنزيل، تحقق SHA-256، تثبيت، رسالة واضحة لو الشهادة غير متوافقة.
- اختبارات JVM + بناء Debug + اختبار يدوي على الهاتف.

**مخرج المرحلة:** APK debug يبني، الواجهة الجديدة تعمل، البلاغ يترفع Online/Offline، وكارت التحديث يعرض حالة السيرفر.

### المرحلة 3 — الاعتماد والموقع في التطبيق

**الهدف:** ربط قرارات الاعتماد والموقع بالواجهة.

- زر واحد «اعتماد وإرسال» مع نتيجة واضحة: «تم الاعتماد» أو «بانتظار المشرف» + سبب.
- شاشة طلب تغيير الموقع للماكينة المقفولة: الموقع الحالي، الجديد، الدقة، صورة إثبات، ملاحظة.
- عرض حالة الطلب: معلّق/موافق/مرفوض، مع إشعار.
- لوحة الإدارة: اعتماد/رفض مع مقارنة الإحداثيات والمسافة.
- اختبارات: شروط الاعتماد، الرفض، outside geofence، mock location، صلاحية معطلة.

**مخرج المرحلة:** سيناريوهات الاعتماد والموقع تعمل على بيانات اختبار، وكل قرار مسجل في Audit.

### المرحلة 4 — الإصدار والتجربة الحقيقية

**الهدف:** أول تحديث حقيقي يصل للأجهزة.

- رفع الإصدار إلى 2.3.0 / code 15 (أو التالي).
- بناء Release من شجرة نظيفة بالمفتاح الصحيح.
- التحقق من manifest وSHA-256 وشهادة التوقيع.
- نشر APK + sidecar على السيرفر عبر السكربت.
- تثبيت على 2–3 أجهزة، واختبار التحديث من النسخة السابقة (أو مسار إعادة التثبيت).
- اختبار دورة كاملة: بلاغ → Issue → إصلاح → إصدار جديد → تحديث.
- اختبار rollback.

**مخرج المرحلة:** جهاز حقيقي واحد على الأقل تم تحديثه، ودورة البلاغ أُغلقت، وrollback يعمل.

### المرحلة 5 — التشغيل والتعميم

- تعميم تدريجي مع مراقبة PM2/health.
- فرز البلاغات أسبوعيًا وربطها بالإصدارات.
- سياسة احتفاظ بالمرفقات (مقترح 180 يومًا) وتنظيف دوري.
- Backup دوري للداتابيز والتخزين، ونسخة offline من keystore.

## 5) معايير القبول النهائية

- لا يوجد أي بلاغ يضيع عند انقطاع الشبكة (طابور محلي + إعادة محاولة).
- كل بلاغ له ملف ZIP وصف Excel، وIssue على GitHub لو مفعّل.
- الاعتماد التلقائي لا يحدث إلا بالشروط، وكل حالة رفض لها سبب ظاهر.
- تغيير الموقع لا يطبق قبل موافقة الأدمن، وكل تغيير له Audit قديم/جديد.
- التحديث يتحقق من الإصدار والهاش وشهادة التوقيع قبل التثبيت.
- APK بشهادة غير معتمدة أو شجرة dirty يُرفض من السيرفر.
- كل الاختبارات القديمة (143) والجديدة تنجح.
- لا أسرار ولا keystore ولا APK في Git.

## 6) المخاطر

- **فقدان مفتاح التوقيع:** أخطر بند؛ يعني عدم القدرة على تحديث التطبيقات المثبتة in-place.
- **اختلاف شهادة التوقيع بين الأجهزة:** بعض الأجهزة قد تكون debug-signed والبعض release-signed؛ لازم جرد قبل الإصدار.
- **السيرفر dirty:** نشر كود جديد قد يمسح تعديلات غير محفوظة؛ لازم فحص وBackup أولًا.
- **GitHub Token في المكان الخطأ:** لا يُوضع أبدًا في التطبيق أو العميل.
- **بيانات العملاء في اللوج:** يجب تنقية السجلات وعدم إرسال أسماء/أرقام العملاء.
- **التثبيت الصامت:** غير ممكن بدون MDM/Device Owner؛ التجربة تنزيل تلقائي + ضغطة تأكيد نظام.

## Additional boundaries and limitations

Encrypted native credential storage exists (`RepAuthStore.java:16-43`), clear uses commit (`:56-57`); worker snapshots token and rep separately (`MadarSyncWorker.java:63-64`) and local read bridge methods accept caller-supplied rep IDs without checking current native identity (`RepNativeEnginePlugin.java:495-514`). Source user UI filters by rep, server authenticates requests; this is not demonstrated native privacy isolation from arbitrary same-WebView script. Logout warns about queued items and disallows active attendance (`RepApp.jsx:1407-1420`), but account switching races remain device-unverified. Native GPS row retention and rejected reasons exist; comprehensive local review tooling does not. Background WorkManager and foreground location service are upload mechanisms, not evidence of closed-app business notification delivery. No Firebase Messaging consumer/device push acceptance was found; optional push remains a product capability decision, not automatically a defect. Source polling25s (`RepApp.jsx:781`) and retry30s (`:1337`) depend on an active app/browser. Server error messages are preserved for permanent4xx, replaced with generic text for transient/auth failures. Startup queue upgrades are additive v1→v3 (`RepLocalStore.java:40-67`); only actual installation acceptance can establish pending-work upgrade preservation.

## J1 — location proposal → supervisor approval → dependent visit

**Chain:** representative opens assigned machine → UI proposes coordinates and records a stable action UUID → IndexedDB/native machine-action queue → native bearer/browser cookie → `POST /api/rep/machines/:machineId/confirm-location ` → rep/assignment/card/coordinate validation → pending review transaction/audit → proposed coordinates persisted separately from approved machine coordinates → HTTP pending response and ` rep.machine.location-requested ` → administrator review UI → approval/rejection HTTP → immediate review/coordinate/audit transaction → postcommit ` rep.machine.location-reviewed` → receiving rep's route refresh → approved coordinates and dependent visit become available, or rejection reason remains visible.

**Producer/consumer/interface:** `RepApp.jsx:1505 ` enqueues actions; ` rep/routes.js:206-218 ` calls service, publishes event and returns200/201. Payload carries ` actionUuid `, ` cardId `, ` location.{latitude,longitude,accuracy,updatedAt}`; machine identity is in route. ` rep/service.js:575-629,700-783 ` handles submit/review; supervisor routes and admin gate are in ` supervisor/routes.js:19-24 `. Queue ownership is representative-scoped; server authenticates independent of caller-supplied identity. Null approved coordinates must remain unknown until approved; pending client state is overlaid without replacing the authoritative approved coordinate (` client/src/modules/rep/location-review.js`).

**Boundary/retry:** service transaction protects pending/review state and audit; event publication is a separate commit (OPS-002). Action identity/content conflict handling and assignment ownership are exercised by isolated HTTP tests. Queue drains required machine actions before dependent visits; approval remains a genuine dependency. A transient failure in unrelated earlier work can still delay visits; see native queue limitation in `android.md`.

**Verification/final state:** seven location tests in `test/location-approval.test.js:70-194 ` pass, including scope/idempotency, rejection/resubmission, concurrent decisions, audit rollback, restart/stale route and dependent upload. This is real local HTTP+SQLite plus one pure client-state test. Native UI/reboot/reconnect review delivery is not physically exercised. Receiving native client uses25s polling rather than EventSource (` RepApp.jsx:769-796`); closed-app alert is unverified. Connection BIZ-C04 and Android machine queue findings apply. Reports must use approved coordinates; pending/rejected proposals are review history, not authoritative location.

**Contract/evidence:** `employees/attendance.js:438-507 ` hashes canonical action content and stores an action UUID; accepted replay lookup precedes age validation. Server max offline age is validated by ` config/env.js:29-37 `, default24hours; age equal to limit is accepted and next millisecond rejected. Future allowance is five minutes inclusive. ` rep/routes.js:157-176 ` publishes attendance/overtime notifications after the service transaction. UI/native enqueue is ` RepApp.jsx:657`; native permanent rejection survives as a review record rather than being silently discarded.

**Authorization/idempotency/retry:** authenticated rep maps to HR employee; another owner or changed UUID content conflicts. An already accepted identical action is returned even after the age window expires. A newly expired action is rejected without affecting attendance or payroll. Authorized administrative corrections/reconciliation are distinct operations with audit. Local biometric success is a client assertion, not cryptographic server proof (AND-006). Auth-required retry must wait for the same owner's valid session; device/account-switch races remain unverified.

**Verification/recovery:** eight focused attendance tests pass, including exact boundaries, ancient punch rejection, old accepted replay, conflicts and admin reconciliation; full 118 suite also passes configuration/startup and HR/payroll lifecycle tests. Initial sandbox subprocess denial is superseded by the successful full run. Physical offline clock-in→process death→reboot→sync→payroll journey was not performed. Rejected-action administrator UX, native privacy/account switching and long-term pending work remain device acceptance gates. Event failure can delay notification but the authoritative attendance API remains the reconciliation source.

An echoed identifier is not durable idempotency. These affect privacy, duty reporting, association and cleanup confidence.

**Verification/recovery:** `gps-repro.mjs ` and primary ` gps-independent-result.json` reproduce both high failures in fresh actual SQLite/service calls: open sessions0→1 after closed-session backlog; fixed ID with changed coordinate/time accepted twice. Release requires late closed-session ingestion without reopening and identical/conflicting/cross-install point identity tests. Connections A-02/A-03; AND-001/002.

## J5 — payment/receipt commit → lost response → retry

**Chain:** authorized finance user enters amount/notes → UI posts settlement → session authentication and finance/admin gate → `POST /api/finance/invoices/:id/receipt ` or `/payment` → amount/balance/kind checks → immediate transaction updates paid/remaining/status and inserts treasury/audit → HTTP result → UI reloads invoice/treasury. If response is lost, user/client repeats the same payload → **new settlement transaction** → duplicated effects.

**Evidence/authorization:** `finance/routes.js:25-30 ` gates both requests; ` invoices.service.js:290-351,361-420` accepts only amount/notes, validates integer cents and prevents overpayment, but has no stable operation ID/content hash/replay ledger. Invoice creation is separated from cash movement; that is a working boundary, not a retry guarantee. A repeated partial amount may still be within remaining balance and therefore duplicate money. A fully paid invoice may reject a retry, which still does not supply response-loss-safe saved-result semantics.

**Verification/failure boundary:** `business-replay-probe.mjs ` and independently rerun ` business-replay-independent.log ` discard the first committed service response, then repeat identical partial settlement for sales and purchase. Each reaches paid2000instead of1000, two treasury records and two invoice audits. Adding ` operationId` is400unsupported. This is an actual service transaction response-loss model, not a TCP packet drop. The existing finance HTTP lifecycle test passes but does not test required idempotency. Concurrency, changed-content and authorization-on-saved-replay cannot be certified because the replay mechanism is absent.

**Reporting/recovery:** treasury, invoice balances and audit show two real effects; historical transactions must not be silently deleted/merged to repair this. Minimal direction is actor-scoped stable operation ID + payload hash + saved response in the same transaction, validated after current authorization. Required acceptance compares invoice/treasury/stock/settlement/audit counts across identical/conflicting/concurrent/response-loss and cross-role retries. BIZ-001; BIZ-C01.
